Multi-council guide

One MCP service can host many councils

Multi-council mode lets one deployed MCP endpoint route each request to a named council profile. The caller chooses the profile with council_id; the service checks authentication and council membership before that profile's OPA rules, chairman, members, ledger, and writ factory run.

Most important rule

The URL stays the same. The request body selects the council.

POST http://host:9901/mcp
tool: council_v2_authorize
arguments.council_id: customer-git

Overview

Use multi-council mode when different workflows need different reviewers, prompts, OPA policy, or risk posture, but should still share one deployed service.

One endpoint

Clients keep using the same hosted MCP URL, usually through the monitor proxy.

Many profiles

Each council_id points to a profile with its own members, OPA policy, ledger, and metadata.

Membership gate

Agent accounts store which councils the identity may petition. Permissions and membership are separate checks.

Hot reload

The registry notices catalog/profile changes on the next request and rebuilds cached council services.

Caller

Agent, test suite, storyboard runner, or integration client sends a normal MCP tool call.

→

Same MCP URL

The monitor forwards to the internal council server. No per-council port exists.

Caller API

New integrations should use the v2 tool names and always pass council_id. Scenario runners use the same API as every other caller.

ToolUse
council_v2_authorizeFull path: evaluate intent and mint a writ if approved.
council_v2_propose_intentReview-only path: evaluate and return the council decision.
council_authorizev1 compatibility. Uses default council if council_id is omitted.
council_propose_intentv1 compatibility. Prefer v2 for explicit multi-council clients.
FieldMeaning
agent_idCaller identity. The authenticated account must match the token.
auth_tokenRaw account token from the account CLI. Required in alpha deployments.
council_idThe review profile to petition. Required for v2 tools.
commandThe action to authorize. Use absolute executable paths unless the council's OPA policy explicitly relaxes that.
description, target_resource, justificationThe semantic context the council evaluates.

Minimal v2 request

{
  "api_version": "v2",
  "agent_id": "storyboard-agent",
  "auth_token": "replace-with-agent-token",
  "council_id": "customer-git",
  "command": "git status --short",
  "working_directory": "/workspace/projects/example",
  "description": "Inspect git worktree state before continuing.",
  "target_resource": "/workspace/projects/example",
  "justification": "Validate the generated council against this workflow."
}
This same payload shape is used by tests, scenario runners, agents, and CI. Dynamic council creation does not add a special validation API.

Runtime Flow

The runtime path is intentionally small. Routing happens before OPA and before LLM work.

Client calls the shared MCP endpoint

The endpoint is independent of council selection. A hosted deployment can expose one monitor URL for every council.

Registry reloads catalog if files changed

The registry fingerprints the catalog and referenced profiles. If the hash changed, it reloads and clears cached council services.

Registry resolves council_id

Unknown councils and disabled councils fail fast. v2 tools require an explicit id; v1 tools may fall back to the default council.

Auth, permissions, and membership run

The token resolves to an account. The account must have action permissions and membership in the selected council.

Selected council evaluates the intent

Only after routing and membership pass do that council's OPA policy, chairman, member prompts, ledger, and writ factory run.

Dynamic Council Creation

Dynamic creation writes configuration. It does not create a second service, expose a new port, or add a new request API.

Recommended workflow: create disabled, inspect and tune the generated profile, grant membership, then enable and run scenario checks against the normal v2 tools.

Create or replace the profile

scripts/councils.sh runs in the council container, so host Python is not required.

Catalog entry is added

The catalog maps the new council_id to councils/<id>.yaml.

Safety defaults are applied

Generated profiles require auth and council membership, and get a per-council ledger path.

Next request reloads it

The registry detects changed files and instantiates the new council only when a request needs it.

Quickstart

        
The short operational path for adding and testing a new council.

      


      

        

          
1. Create

          
./scripts/councils.sh create customer-git \
  --template strict-production

        

        

          
2. Grant access

          
./scripts/agent_accounts.sh create storyboard-agent \
  --role developer --council customer-git

        

        

          
3. Validate

          
council_v2_propose_intent({
  "agent_id": "storyboard-agent",
  "council_id": "customer-git"
})
