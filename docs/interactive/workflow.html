Nomos workflow

From agent intent to signed execution

This walkthrough explains the current authorization path: monitored MCP ingress, optional multi-council routing, OPA filtering, LLM council review, writ minting, executor verification, and audit visibility.

Core invariant

  1. The agent asks before it acts.
  2. The council signs the exact approved action.
  3. The executor verifies the writ before running anything.
  4. The ledger records the decision trail.

Runtime Map

One external MCP endpoint can serve multiple council profiles. The monitor is the public entry point; the council service stays internal to the Docker network.

Agent or IDE

Calls MCP or gRPC with `agent_id`, token, intent details, and optionally `council_id`.

Monitor

Terminates external MCP traffic, forwards to council, records latency, source, tool, and recent request state.

Council

Authenticates, routes to the selected council, filters through OPA, runs review, and mints writs.

Redis and OPA

Redis stores accounts, permissions, memberships, writ metadata, nonces, and rate limits. OPA handles deterministic policy.

Executor

Receives signed writs, verifies contract and local policy, claims nonce, and performs the actual operation.

Full Authorization Workflow

`council_authorize` and `council_v2_authorize` evaluate an intent and return a signed writ when the request is approved.

01

Agent submits the exact intended operation

The request includes command, working directory, target resource, description, justification, blast radius, context, evidence, and optional packaged files.

MCP/gRPC ingress council_v2_authorize
02

Monitor forwards and observes

The monitor preserves the request, forwards it to the internal council MCP server, and records source attribution, latency, status, and JSON-RPC method.

external port 9901 X-Council-Source
03

Registry selects the council

v1 requests without `council_id` use the catalog default. v2 requests must specify a known council id.

catalog routing configs/local_council_catalog.yaml
04

Authentication and membership run first

The token resolves to an account in Redis. The authenticated identity wins over caller-supplied `agent_id`, and the agent must be a member of the selected council.

fail closed nomos:accounts:{agent_id}
05

Command shape becomes policy input

The council categorizes required permissions and builds a normalized intent document for OPA, including shell command words, packaged-file metadata, account permissions, and council memberships.

deterministic gate /v1/data/nomos/intent/decision
06

OPA denies obvious policy violations

OPA can reject missing absolute paths, sensitive directory access, remote-fetched execution, unsafe packaged files, or council-specific relaxed-profile violations before LLM work begins.

pre-council deny policy_id: strict-shell
07

Code Review inspects attached files

When packaged files are included, the code-review sidecar evaluates decoded contents. Its analysis is injected into council context and file hashes are later bound into the writ.

attachments packaged_files[]
08

Chairman sets the voting threshold

The chairman assesses risk and chooses unanimous or quorum where explicitly allowed. By default quorum is disabled, so the threshold clamps to unanimous.

risk threshold chairman.allow_quorum
09

Council members vote in parallel

Each configured member receives the same structured intent, code-review context, and council-specific priorities. Optional debate rounds can re-run evaluation with peer positions.

LLM fanout members[]
10

Approval mints a signed writ

The writ locks the council id, target agent, command, working directory, expiry, nonce, packaged-file hashes, and ledger linkage into signed bytes.

Ed25519 WritOfExecution
11

Executor verifies before running

The trusted executor checks contract version, target agent, signature, expiry, nonce, exact command, packaged-file integrity, and local policy. Council approval is necessary but not sufficient.

defense in depth POST /v1/writs/execute
12

Outcome is recorded

The executor returns exit code, stdout, stderr, and duration. Redis stores writ outcome metadata and the ledger records council-side decisions.

audit trail nomos:writs:{writ_id}

Propose-Only Workflow

`council_propose_intent` and `council_v2_propose_intent` answer "would this be approved?" without minting a writ.

What still runs

  • catalog routing and council selection
  • authentication and council membership checks when auth is required
  • permission categorization
  • OPA filtering
  • code review for attached packaged files
  • chairman threshold assessment
  • member voting and optional debate

What does not happen

  • no writ is minted
  • no executor call is made
  • no command can run from this response alone
  • the response is advisory guidance for the calling agent

Denial Paths

Denials are intentionally informative. The goal is to help well-intentioned agents repair scope, evidence, and permission problems without bypassing the review boundary.

Where denial happens Typical cause What the agent should do
Authentication Missing token, rotated token, disabled account, Redis unavailable in fail-closed mode. Refresh credentials or ask an operator to inspect the account.
Council membership The authenticated agent is not allowed to petition the selected `council_id`. Use the default council or request membership through account management.
OPA Deterministic policy violation such as bare executable path, sensitive path, or unsafe attachment. Reformulate the command, use absolute paths, narrow scope, or choose a council with an explicit relaxed profile.
Chairman or permissions The requested action needs permissions the agent does not have. Stop or ask for a role/permission change. Do not route around the boundary.
Council members The action is too broad, under-evidenced, contradictory, or unsafe for the claimed blast radius. Add evidence, provide rollback, reduce scope, or choose a safer command.
Executor The writ is valid but local executor policy rejects the exact command, path, tool, file, nonce, or environment. Respect local policy. Request a different executor profile only when operationally justified.

Multi-Council Routing

Council choice is a request property, not a port choice. Membership is separate from action permissions.

v1 default path

Use v1 or unversioned tools when a client should simply petition the deployment's default council.

  • `council_id` can be omitted.
  • The registry resolves to `default_council_id`.
  • This preserves older clients.

v2 explicit path

Use v2 tools when the caller intentionally selects a specialized council.

  • `council_id` is required.
  • The id must exist in the catalog.
  • The authenticated agent must be a member of that council.

Operator rule: add new review profiles to the catalog, grant membership explicitly, and keep one external MCP endpoint unless there is a clear isolation reason to run a separate deployment.

Ledger and Monitor

The monitor shows request traffic and reads council ledger files without importing council internals.

Live request view

  • tracks JSON-RPC methods only
  • separates council throughput from other traffic
  • records source attribution for direct, gRPC, and demo traffic
  • shows council stage and actor latency telemetry

Cryptographic ledger browser

  • loads ledger pages lazily by cursor
  • keeps list DOM bounded with Previous and Next pagination
  • redacts tokens, credentials, and secret-like fields
  • checks content hashes and adjacent hash-chain links where available

Operator View

These are the configuration surfaces operators usually touch when changing behavior.

Surface Owns Common edits
configs/local_council_catalog.yaml Which councils run in one MCP service. Add a council, set default council, set process-level NAT listener.
configs/council.yaml Default production council profile. Change members, prompts, backends, OPA policy, ledger path.
configs/git_workflow_council.yaml Git-workflow specialized council. Tune git and GitHub CLI review rules, relaxed OPA profile, quorum opt-in.
scripts/agent_accounts.sh Agent accounts, permissions, council membership. Create users, rotate tokens, grant or revoke council membership.
deploy/docker-compose.yml Local Docker deployment topology. Expose monitor, mount ledger, configure OPA, Redis, gRPC, demo, executor.
deploy/executor*.yaml Executor-local policy. Allow tools, block arguments, set working directories, configure sandbox behavior.
