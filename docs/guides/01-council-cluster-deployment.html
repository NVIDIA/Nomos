How the pieces talk

External agents only ever hit the monitor — never the council directly. The monitor enforces auth (Basic on dashboard, Bearer on /mcp), strips traffic of identifying headers it shouldn't forward, and writes per-source metrics.

The council holds the signing key on a 0400 PVC. Lose it and every previously-issued writ becomes unverifiable. Back it up.

OPA is consulted before council members vote — it is the cheapest place to reject obviously-bad intents. The bundled policy lives in policies/intent_filter.rego; deployments can supply their own.

Secret material at a glance

  • NVIDIA_API_KEY — LLM backend access. Required.
  • REDIS_PASSWORD — Redis AUTH. Required outside dev.
  • COUNCIL_REDIS_ACCOUNT_INTEGRITY_KEY — HMACs account records against direct Redis tampering. Required.
  • MONITOR_MCP_PROXY_TOKEN — Bearer token gating /mcp. Required.
  • MONITOR_DASHBOARD_PASSWORD — Basic auth on / and /api/*.
  • MONITOR_INTERNAL_TOKEN — Council-→-monitor telemetry channel.

The actual install

helm · single command after secret

Generate secrets

One openssl rand -hex 32 per secret. Keep them out of values files and Helm history.

Create Secret

One Kubernetes Secret named nomos-secrets. The chart reads from it.

Helm upgrade

Run with deployProfile=alpha so preflight refuses dev-default values.

Verify

Three checks below: pods alive, MCP responding, council actually mints a test writ.

Provisioning the Secret

bash
# Generate strong random material for everything except the LLM key.
ACCOUNT_INTEGRITY_KEY=$(openssl rand -hex 32)
COUNCIL_MGMT_TOKEN=$(openssl rand -hex 32)
MONITOR_INTERNAL_TOKEN=$(openssl rand -hex 32)
MONITOR_DASHBOARD_PASSWORD=$(openssl rand -hex 24)
MONITOR_MCP_PROXY_TOKEN=$(openssl rand -hex 32)
REDIS_PASSWORD=$(openssl rand -hex 32)

kubectl create namespace nomos

kubectl -n nomos create secret generic nomos-secrets \
  --from-literal=NVIDIA_API_KEY="$NVIDIA_API_KEY" \
  --from-literal=REDIS_PASSWORD="$REDIS_PASSWORD" \
  --from-literal=COUNCIL_REDIS_ACCOUNT_INTEGRITY_KEY="$ACCOUNT_INTEGRITY_KEY" \
  --from-literal=COUNCIL_MANAGEMENT_TOKEN="$COUNCIL_MGMT_TOKEN" \
  --from-literal=MONITOR_INTERNAL_TOKEN="$MONITOR_INTERNAL_TOKEN" \
  --from-literal=MONITOR_DASHBOARD_USER=admin \
  --from-literal=MONITOR_DASHBOARD_PASSWORD="$MONITOR_DASHBOARD_PASSWORD" \
  --from-literal=MONITOR_MCP_PROXY_TOKEN="$MONITOR_MCP_PROXY_TOKEN"

Helm install

single command
helm upgrade --install nomos deploy/kubernetes/nomos \
  --namespace nomos \
  --set secrets.create=false \
  --set secrets.existingSecret=nomos-secrets \
  --set deployProfile=alpha \
  --set networkPolicy.enabled=true

What each flag does

  • secrets.create=false — chart reads the pre-created Secret instead of building one from values (which would persist in Helm history).
  • deployProfile=alpha — every service runs a preflight; refuses to start if any required secret is unset or matches a known dev default.
  • networkPolicy.enabled=true — applies the bundled NetworkPolicies. Only effective on a CNI that enforces them (kindnet does not; Calico/Cilium do).

Customizing council.yaml

members · backends · chairman

Backends

Each member references a named backend. Default routes everything through NV Cloud Functions. Switch to anthropic, openai, or nim per backend; add the matching API key to the Secret.

llm_backends:
  primary:
    provider: anthropic
    model: claude-sonnet-4-20250514
    api_key: "${ANTHROPIC_API_KEY}"
    temperature: 0.0

Members

Three independent reviewers by default — Command Integrity, Environment Isolation, Blast Containment — voting unanimous. Each can target a different backend so a single vendor outage doesn't blind the council.

members:
  - id: command-integrity
    backend: primary
    weight: 1
    priorities: [ ... ]

Chairman

The chairman picks the threshold; it does not vote. Quorum is disabled by default. Enable explicitly only if you understand that low-risk reads will then need just a simple majority.

chairman:
  enabled: true
  backend: primary
  allow_quorum: false

Exposing the council

monitor is the only entry point

Ingress (recommended)

Front the monitor with your ingress controller. Agents call https://nomos.example.com/mcp with Authorization: Bearer ${MONITOR_MCP_PROXY_TOKEN}.

The dashboard at / is gated separately by Basic Auth. The two credentials are independent on purpose.

gRPC

The gRPC service exposes the same MCP tools as a binary protocol on port 9904. Use this for high-rate IDE/CI clients that don't want JSON-RPC overhead.

The gRPC proxy forwards through the monitor, so the same Bearer token is required.

Same-cluster

Agents living in the same Kubernetes cluster skip ingress entirely — they call http://nomos-monitor.nomos.svc.cluster.local:9901/mcp directly.

The MCP proxy token is still required.

Verification ladder

do not skip
1. Pods are alive

kubectl -n nomos wait --for=condition=available deploy/nomos-council --timeout=180s
Repeat for deploy/nomos-monitor and the Redis StatefulSet rollout.

2. The council answers MCP

curl -s -H "Authorization: Bearer $MCP" https://nomos.example.com/debug/tools/list | jq '.tools[].name'
Expected: an array containing propose_intent, check_proposal_status, approve_intent, execute_intent, get_ledger_status.

3. The council actually mints

uv run ./scripts/run_test_suite.py --suite mcp-live --require-deployed --council-url https://… --council-token "$MCP"
Submits a low-risk intent, expects approval, confirms a writ comes back. Failures here are almost always misconfigured backend keys or an OPA deny.

What's now persistent

four PVCs survive restarts

Council Ed25519 Keys

If lost: every prior writ becomes unverifiable; every executor must reload. Back this up.

Ledger

Hash-chained JSONL audit. Loss is operational, not a security failure.

Redis Data

Accounts · nonce store · in-flight writs. Loss resets active workflows; agents must re-propose.

Monitor Cache

Dashboard static assets. Cosmetic.

Single-VM Compose path

For solo development or an isolated VM, the same stack runs under Docker Compose. NVIDIA_API_KEY=… DEPLOY_TARGET=compose ./scripts/deploy_stack.sh generates deploy/.env at mode 600 and brings everything up.

Not suitable for production: no horizontal scaling, no namespace isolation, no NetworkPolicy.
