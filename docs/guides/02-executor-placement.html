The council is a remote MCP endpoint your agent already knows how to reach. The real decision is about the executor: what form it takes, where it lives relative to your agent, and how the agent reaches it.

Premise

Agents are almost never co-located with the council. The council is just a URL — your agent submits an intent over MCP and waits for a signed writ. The placement question is about the executor, and the answer depends on what your agent is trying to manage. Situation 1 — Self-managing host

Mental model: the agent is software that maintains the box it runs on — package updates, log rotation, restarting its own services, running maintenance scripts against local files.

Why an executor anyway? The agent never executes commands directly. Even though the executor is right next to it, going through the writ pipeline gives you signed authorization, an audit trail, and a real chance to catch the agent doing something it shouldn't. Without it, "the agent decided to rm -rf" is just a log line.

Concrete shape: two containers on the same Docker host, or two systemd units on bare metal. The executor binds 127.0.0.1:9906. The agent calls http://localhost:9906/v1/writs/execute.

What you actually have to set up

  • An executor configured with the council's public key (pinned at public_key_path).
  • The executor's identity key (its own Ed25519 pair) for signed evidence.
  • Network reach from the executor to the council Redis nonce store. The agent doesn't need it.
  • Localhost binding on the executor's port. The outside world should not see it.

Watch out: any other process on the host with reach to :9906 can submit writs. Use a unix socket or a firewall rule if other users share the box.

Situation 2 — Fleet of machines

Mental model: one agent oversees N machines. Each machine runs its own executor; the agent picks which executor receives each writ based on the intent's target_host or equivalent field.

Why per-host? Two reasons. (1) The blast radius of a compromised executor is bounded to its own host. (2) The writ's working_directory means something different on each host — letting one executor act on multiple machines would erase that meaning.

Concrete shape: each host runs the same executor image with a distinct identity key. The agent keeps a registry: hostname → executor URL.

Do not give each host its own key_prefix. The prefix scopes the trusted-executor registration key as well as the nonce keys, so a per-host prefix writes the registration where the council does not look — certified evidence from that executor is then never recognised. Share the council's prefix; nonces are already unique per writ. Do not reach for a per-host Redis as the isolation mechanism either — see the nonce-store note below.

What you actually have to set up

  • One executor per host with a distinct identity_private_key_path on each.
  • One shared nonce store across every executor, with the same key_prefix as the council. A separate Redis per host does not work: a writ carries target_agent_id but no target executor, and each executor claims the nonce with SET NX in its own Redis — so one captured writ would be claimable once on every host, which is exactly the replay the nonce exists to prevent.
  • An addressing scheme the agent can use — DNS, service discovery, a config file mapping host-a → https://exec-a.internal:9906.
  • The intent should carry enough information (target_host, target_environment) for the council to reject mis-targeted writs before they reach the wrong executor.

Watch out: a writ is currently bound to a target agent, not a target executor. Until that changes, harden by giving each executor a distinct council subkey, or by validating working_directory against the executor's allowed roots.

Situation 3 — Provisioned management host

Mental model: the executor is a privileged bastion that holds the credentials to drive a target system. The agent has no creds; the bastion does. Classic example: an executor with a working kubeconfig against a specific cluster.

Why this shape? You don't want every machine running an agent to hold cluster credentials. Concentrate the trust in one well-monitored process. The agent just submits writs against a stable endpoint; if it's ever compromised, what it can do is exactly what the bastion's role grants — nothing more.

Concrete shape: a single executor pod / VM with the kubeconfig (or IAM role, Terraform Cloud token, Snowflake user, etc.). The executor exposes :9906 on its private network; the agent reaches it over mTLS or a shared-secret Bearer header.

What the executor is doing

This is the case where the writ's command isn't literally a shell command — it's a description of an action the executor maps onto a managed-service call.

  • kubectl-executor — writ → kubectl apply -f - / kubectl exec against the bound cluster.
  • aws-ssm-executor — writ → ssm SendCommand against a tagged instance set.
  • terraform-cloud-executor — writ → triggered run on a specific workspace.
  • snowflake-executor — writ → GRANT / REVOKE on a database role.

You write this executor yourself. The HTTP contract and a working FastAPI skeleton are in Guide 3 §B.

Three decisions you have to make

the answer depends on the situation above

Decision 1

Form of the executor

What does the executor actually do when it runs a writ? Pick from the two shipped or write a custom one.

Self-managing host Usually executors/docker (hardened sandbox) or executors/openshell (persistent /workspace).
Fleet Same shipped executors, one per host. Identical config except identity key and nonce prefix.
Bastion Custom executor. The writ's command maps to a managed-service API call.

Decision 2

Where it's located

Where does the executor run? The constraint is: the executor needs reach to whatever it controls and to the council's Redis.

Self-managing host Same machine as the agent. Same Docker host or same systemd target.
Fleet One per managed host. The executor lives on the thing it manages.
Bastion A dedicated management VM / pod. Network-adjacent to the target system; isolated from the agent.

Decision 3

How the agent talks to it

What URL does the agent POST writs to? The answer changes the auth posture too.

Self-managing host http://127.0.0.1:9906. No TLS needed; firewall the port off the public interface.
Fleet Per-host URL: https://exec-{host}.internal:9906. mTLS or shared Bearer at the executor edge.
Bastion Single URL: https://bastion.internal:9906. Tight ingress allowlist for agent identities.

True in every situation

trust establishment is the same shape

1. The council signs

On first start the council generates an Ed25519 key pair. The public component is the only thing an executor needs to verify writs. It's also reachable via the council_get_public_key MCP tool if you'd rather fetch than mount.

2. The executor pins

Every executor — local, per-host, or bastion — sets council.public_key_path to a file containing those 32 bytes. When that file is present the executor uses it and never fetches, so the trust anchor is already pinned. (key_fetch_retries is validated as >= 1 and is not currently read by the fetch path; setting it to 0 only makes the config fail to load.)

3. The executor identifies

Each executor instance has its own Ed25519 identity key. On startup it registers in Redis under nomos:trusted_executors:{fingerprint}. Future intents can require evidence signed by a registered executor — certified evidence.

executor.yaml — trust anchor

yaml · same across all situations
# Pinned public key is THE trust anchor. Mount it; do not fetch.
council:
  public_key_path: "/app/public-keys/council.pub"
  url: "https://nomos.example.com"  # base only -- the executor appends /mcp

# Executor's own identity. Distinct per instance.
executor:
  identity_private_key_path: "/app/executor-keys/executor.key"
  identity_public_key_path:  "/app/executor-keys/executor.pub"
  listen_host: "127.0.0.1"      # or 0.0.0.0 behind network policy
  listen_port: 9906

# Nonce store reach: agent doesn't need it; executor MUST.
redis:
  url: "redis://council-redis.example.com:6379/0"
  key_prefix: "nomos:"           # MUST match the council's prefix

always serve these
# Liveness + capabilities + executor identity fingerprint

End-to-end check

Have the agent propose a low-risk intent (ls /workspace for a shipped executor; kubectl get pods -n default for a kubectl bastion). The response should carry verification_stage: "passed" and a signed evidence block. Guide 3 shows the agent side.

The reachability checklist

  • Agent → Council MCP · always. The only way to mint writs.
  • Agent → Executor /v1/writs/execute · always. localhost, per-host URL, or bastion URL depending on situation.
  • Executor → Council Redis · always. Without nonce dedup, writs are replayable.
  • Executor → its target · the whole point — local subprocess, host resources, or managed-service API.
  • Council → Executor · never required. The agent is the courier.
