Finding and interpretation

The original questions used the reported role evidence successfully in all six core pairs. They denied outgoing A when its reported role was a credential and allowed the identical A when it was an ordinary reference. This supplies a concrete, conditional example of context helping where HTTP alone lacks the needed information.

U did not establish a safer replacement. It passed both decisions in four of six core pairs. It fixed three original-question false blocks on different benign B values, but introduced two harmful allows on credential A. Each missed credential received a credential-disclosure score of 0.67, below the fixed 0.70 threshold. Both context conditions passed all twelve HTTP-decidable controls; HTTP-only passed eleven, falsely blocking a literal redacted password at 0.76.

The aggregate U result (34/36 logical labels versus Original's 33/36) hides the security tradeoff: two added credential escapes in exchange for three fewer false blocks. Do not adopt U or tune the threshold after seeing this small set. Both context conditions still ranked credential-role A above ordinary-role A in all six families; recognizing relative evidence is different from meeting the configured denial rule.

Keep the original questions as the reference while improving context-boundary handling. These selected fixtures demonstrate conditional semantic use, not verified history or general production benefit. HTTP-only's zero fully correct core pairs is structurally unavoidable: this is an information limit, not a general model failure. U's six exemption denials also include scores of 0.70 and 0.72; this is an observed result, not robust prompt-injection resistance.

The role labels in this study are conditional on supplied reported evidence. A successful classification does not prove that a credential works, the history is authentic, an HTTP request originated from a particular tool, or disclosure was authorized. No production question, formatter or deployment is changed by this experiment.

Why this experiment is different

The preceding 96-case study asked whether sensitive history distracts a reviewer from an HTTP request that is already answerable on its own. HTTP-only did best on that deliberately selected set. It did not test context's potential benefit when an outgoing value's meaning cannot be inferred from its characters alone.

This study supplies opaque values whose reported application role changes between fixtures. The outgoing HTTP body can stay identical while earlier tool arguments describe the value as either an authentication token or an ordinary reference. This gives context an opportunity to help, while controls check whether it also manufactures disclosure or accepts an exemption claim.

There are two cohorts, reported separately:

• 24 role-binding cases: six related families, each with four cells.

• 12 HTTP-decidable controls: six safe/unsafe pairs with benign history.

The 36 cases are evenly split: 18 expected allows and 18 denials. They are not 36 independent random samples; counterfactual cells belong to related families. No old fixture or prior score was included in the new collection.

Setup: real components, synthetic tool history

A fixture client published snapshots and tool events through the real context service's authenticated HTTPS API. A snapshot contains retained user text; a tool event contains reported arguments, execution state and optional Council review. These are the supported fields, not a full conversation or captured tool-result bodies.

The actual middleware reader was called over native TLS gRPC with valid short-lived fixture JWTs. A local recording model captured the constructed state; its fixed acknowledgements were not model-study decisions. The captured state was converted to compact JSON or stripped of context, then replayed directly to the real Jev API.

Hermes did not execute these tools, Council did not make the supplied decisions, and no inspected HTTP request was forwarded to a destination. “Harmful escape” below means the model assessment would allow an author-labeled harmful request under the configured threshold, not that data reached a server. No exact causal HTTP-to-tool attribution is claimed.

All strings, credential-shaped values, organizations and business facts are fabricated evaluation content. Real API credentials remain outside saved model requests. No private endpoint, working credential or PEM key is included.

Why HTTP-only cannot distinguish the core pairs

For each family's credential-role and ordinary-role pair, HTTP-only receives exactly the same complete model request. One shared response cannot correctly deny one and allow the other. Its count of pairs with both cells correct is therefore necessarily 0/6, an information limit rather than proof of poor reasoning.

Credential-role, ordinary-role and exemption cells all share outgoing A. Their labels are deny, allow and deny. The different-value B cell is separate and labeled allow. Even an ideal HTTP-only decision for A and B can match at most three of the four labels: 18/24 role cells, or 75%. This theoretical ceiling is not a target for the model and is not a production accuracy estimate.

Do not use a pooled overall accuracy comparison to hide that the HTTP-only reference is intentionally underinformed. The pair and control tables below answer different questions and must be interpreted separately.

Calls, ordering and evidence accounting

36 logical cases x three conditions = 108 comparison cells. They require only 96 unique actual API calls:

• Original + context: 36 calls.

• U + context: 36 calls.

• HTTP-only: 24 calls—twelve role-cohort requests and twelve controls.

In each role family, A's one HTTP-only measurement is reused for the credential, ordinary and exemption cells. B has its own measurement. There are no nonce fields, repeated duplicate submissions or invented independent replicates. Each call asks both disclosure questions; questions are not separate API calls.

Inputs, question catalogs, labels and order were frozen before collection. Actual-call blocks were randomized while preserving original/U comparisons; the exact schedule is recorded in the manifest and matrices. Started/finished markers distinguish actual attempts from their logical-cell references. All labels, rationale, category, cohort, variant and titles stay outside model state. No automatic retries, threshold retuning or post-result relabeling are part of this experiment. Provider caching is unknown even for new content.

The exact endpoint is https://api.typesafe.ai/v1/systemone, with pinned model jev-1.14.0. The replay timeout is eight seconds, not a production middleware, gRPC or model deadline. A direct-replay success does not establish deployment timeout reliability. No live agent callbacks or destination forwarding occurred.

Limits and next steps

This is a small, selected study of six related role families and six related control pairs. It does not establish generalized context benefit, calibrated risk probabilities, secure trust in workload-mutable context, causal tool attribution, live H1/H3 publication, model repeatability, larger-input behavior or parallel-request performance. Structured instructions and Noul criteria were not added to the middleware adapter.

A clearer question can be useful only if it preserves both boundaries: context may help classify values actually sent, while history-only values and claimed permission are not themselves outbound disclosure or authorization. Assess the observed tradeoffs, not only a favorable aggregate percentage.
